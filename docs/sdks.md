# Generated clients and SDK packaging

Kayak generates four clients from the contract: Rust, TypeScript,
Python, and Go. Each is one self-contained file under
[`clients/`](../clients/), regenerated by the contract test and
compared byte for byte against the checked-in copy. Nobody edits them
by hand.

## What the clients cover

The clients cover the JSON routes the contract declares:

- Files: list, get, create, remove, list versions, issue a signed read
  URL, issue an upload URL, issue an edge URL, request a rendition,
  request a transform, and fetch from a URL.
- Webhooks: list, get, register, remove, and list deliveries.
- Events and runs: list and get, plus start and retry for runs.
- Search and a file's extracted text.

List methods take `limit` and `cursor`. Filters and sort orders are
not exposed as method arguments.

## Limits to know before you use them

**They authenticate with the tenant header only.** The contract
declares header authentication (`x-copal-tenant`), so every generated
client sends that header and nothing else. They cannot send an API key
(`Authorization: Bearer ck1...`). In practice they work only against a
server running `COPAL_AUTH_MODE=header`, the development mode. Against
a `keys` deployment every call answers 401.

**They have no byte methods.** Uploading content
(`PUT /v1/files/{id}/content`), downloading it, version content,
resumable uploads (`/v1/tus`), grant redemption, and the S3 gateway
are outside the contract, so no client method exists for them. Use a
plain HTTP client for bytes. One pattern that works with the clients
as they are: create the record, issue an upload URL, and `PUT` the
bytes to that URL, which needs no credentials.

`GET /v1/usage` and the admin surface are also outside the contract
and have no client methods.

## Packaging

The packages are assembled from the generated files:

```
sdks/
  VERSION            one version for all four, for example 0.1.0
  rust/              Cargo.toml skeleton for crate oneiriq-copal (library name copal)
  python/            pyproject.toml skeleton for package oneiriq-copal (module copal)
  typescript/        package.json and tsconfig.json for @oneiriq/copal
  go/                go.mod for github.com/Oneiriq/copal-go
  build.sh           assembles into sdks/dist and validates all four
```

`bash sdks/build.sh` copies each generated client into its skeleton
under `sdks/dist/<language>`, stamps the version from `sdks/VERSION`,
and validates each package: `cargo check`, `py_compile` plus an
import, `tsc --noEmit`, and `go build` with `go vet`.

CI runs the same script in its `sdks` job. The CI workflow
(`.github/workflows/ci.yml`) has three jobs (`check`, `sdks`, and
`console`) and runs on pull requests to `main`, on a daily schedule,
and on manual dispatch. A client that stops compiling in any language
fails the pull request that broke it.

## Publishing

None of the four packages is on a registry yet. The names are
reserved in the manifests only:

| Language | Package |
| --- | --- |
| Rust | crates.io `oneiriq-copal` |
| Python | PyPI `oneiriq-copal` |
| TypeScript | npm `@oneiriq/copal` |
| Go | module `github.com/Oneiriq/copal-go` |

Publishing is manual. `.github/workflows/publish-sdks.yml` runs only
on manual dispatch and dry-runs by default. Bump `sdks/VERSION`, then
dispatch the workflow with `dry_run: false` once registry tokens exist.
Go modules version by tag, so for Go the workflow prints the tag to
cut on the `copal-go` repository after the assembled module is pushed
there.

For license terms, read each package's own manifest under `sdks/`.
